# Logistics Operations Dashboard

## Next.js + Tailwind Mock Logistics Operations System

---

## 1. Project Objective

Build a realistic logistics operations dashboard for showcase purposes.

The application represents an active logistics control centre where staff monitor:

* Deliveries
* Truck movements
* Driver activity
* Operational events
* Emergencies
* Delays
* Support tickets
* Route progress
* Staff activity

The system is a simulation. It must behave as though it is receiving live operational information.

The application should **not contain generic placeholder content** such as:

* "Lorem ipsum"
* "Test Event"
* "Sample Driver"
* "Truck 123"
* "Example Ticket"
* "Placeholder"
* "TODO"
* "Mock data"

All simulated information should resemble legitimate logistics operations.

Examples:

* "Vehicle PBX-4821 delayed approaching N1 Midrand interchange"
* "Delivery to East Rand Distribution Centre completed"
* "Driver Thabo Mokoena reported tyre pressure warning"
* "Emergency brake-temperature alert received from PBX-7194"
* "Consignment PB-84721 expected 18 minutes late"

---

# 2. Technology

## Frontend

* Next.js
* TypeScript
* Tailwind CSS
* React
* Server/client components where appropriate

## State

Use a central simulation state rather than scattering state throughout UI components.

Recommended structure:

```text
Simulation Engine
        |
        v
Application State
        |
        +---- Events
        +---- Trucks
        +---- Drivers
        +---- Tickets
        +---- Staff
        +---- Routes
        |
        v
Dashboard Components
```

The simulation engine owns the changing world.

UI components consume state and emit user actions.

# 9. Status Visual System

The UI should communicate operational importance immediately.

## Critical / Emergency

Emergency events use:

```text
red indicator
```

The indicator should pulse/flash continuously.

Example:

```text
● EMERGENCY
```

The animation should be implemented using Tailwind animation utilities or a custom Tailwind animation.

Critical cards should visually stand out without becoming visually chaotic.

---

## Warning / Potential Late

Potential delays use:

```text
orange indicator
```

Examples:

```text
18 min behind schedule
Traffic delay
Estimated arrival slipping
Driver approaching shift limit
```

Orange means:

> Attention required, but not an emergency.

---

## Normal

Normal operational activity should use a neutral/positive visual state.

Examples:

```text
Delivery completed
Truck departed
Driver arrived
Route progressing normally
```

---

## Resolved

Resolved events should become visually subdued.

The information remains available for operational history but should no longer dominate the dashboard.

```text

```

A fully typed LogisticsEvent instance.

### Pseudocode

```text
CLASS LogisticsEvent:

    CONSTRUCTOR(eventData):
        assign event properties
        calculate initial state

    resolve():
        status = RESOLVED
        resolvedAt = current time

    escalate():
        severity = CRITICAL
        status = ESCALATED

    updateStatus(newStatus):
        validate status
        status = newStatus

    increaseSeverity():
        change NORMAL -> WARNING
        change WARNING -> CRITICAL

    decreaseSeverity():
        change CRITICAL -> WARNING
        change WARNING -> NORMAL
END
```

```text
        select possible activity
```

The simulation interval should be configurable.


# 23. simulation/EventGenerator.ts

### Purpose

Creates realistic operational events.

### Functions

```text
generate()
generateDelay()
generateDelivery()
generateVehicleAlert()
generateDriverAlert()
generateEmergency()
generateTicket()
```

### Output

A new domain event.

### Pseudocode

```text
generate():

    inspect current simulation state

    choose event category based on weighted probabilities

    IF emergency probability:
        generate emergency

    ELSE IF delay probability:
        generate delay

    ELSE IF delivery probability:
        generate delivery

    ELSE IF vehicle activity:
        generate vehicle event

    ELSE:
        generate normal operational activity
END
```

Use weighted randomness rather than completely random randomness.

Emergency events should be rare.

Normal events should dominate.

# 50. Simulation Behaviour

The simulation should not simply change random values.

It should model cause and effect.

For example:

```text
Traffic event
    ↓
Truck speed decreases
    ↓
ETA increases
    ↓
Route becomes WARNING
    ↓
Orange indicator appears
    ↓
Delay event added
    ↓
Ticket may be created
```

Similarly:

```text
Vehicle telemetry anomaly
    ↓
Warning
    ↓
Critical threshold
    ↓
Emergency
    ↓
Driver status changes
    ↓
Truck status changes
    ↓
Urgent ticket
    ↓
Dispatcher assignment
```

This creates the perception of a living system.

---

# 51. Event Probability Model

Recommended approximate distribution per simulation cycle:

```text
Normal operational activity     50%
Delivery activity               15%
Vehicle activity                10%
Traffic/delay activity           10%
Driver activity                  8%
Ticket activity                  5%
Emergency activity               2%
```

These are guidelines rather than fixed values.

Emergency events should remain uncommon.

The system should never feel like it is intentionally trying to create emergencies.

# 52. Event Lifecycle

Events should have lifecycles.

Example:

```text
CREATED
   ↓
ACTIVE
   ↓
MONITORING
   ↓
RESOLVED
```

Or:

```text
CREATED
   ↓
ACTIVE
   ↓
ESCALATED
   ↓
RESOLVED
```

The simulation should occasionally progress existing events rather than continuously generating new ones.

This is critical for realism.

Some tickets should remain open for longer than others.

Some warnings should resolve automatically.

# 67. Session 2 Enhancement Requests

The following requests were made after the initial build and have been implemented. They are recorded here for context so future changes remain consistent with them.

## 67.1 Card Insert / Reorder Animation

- New cards (events, trucks, drivers, tickets) must animate in individually rather than appearing abruptly.
- Existing cards must animate downward/reflow smoothly to make space for a new card at the top of a list.
- When an existing card is updated (status change, escalation, resolution, reassignment), it should animate to the top of its own section rather than jumping instantly.
- Implemented using `framer-motion` (`AnimatePresence` + `motion.div layout`) in EventFeed, TruckActivity, DriverActivity, TicketPanel, ActivityTimeline.
- To support "move to top on update", domain classes (`LogisticsEvent`, `Truck`, `TruckDriver`) track a `lastUpdated` timestamp that refreshes on every mutating method. Lists sort primarily by this recency (with truck/driver activity keeping status-priority as the primary sort and recency as the tiebreaker, and tickets keeping priority as the primary sort with `updatedAt` recency as the tiebreaker).

## 67.2 Working Sidebar Navigation

- The left sidebar navigation (Overview, Live Operations, Fleet, Drivers, Tickets, Events, Reports) must actually switch the dashboard's visible content, not just be decorative links.
- Implemented as client-side view state (`DashboardView`) in `state/dashboardReducer.ts` / `state/DashboardProvider.tsx`, rather than separate Next.js routes, so the single `SimulationEngine` instance is not torn down/remounted when switching views.
- `Dashboard.tsx` renders different panel combinations depending on the active view (e.g. Fleet shows full-width Truck Activity, Reports shows Activity Timeline + Ticket Panel).

## 67.3 Managers On Duty (Sidebar)

- A "Managers On Duty" list of 4 managers appears in the left sidebar below the navigation.
- Each entry shows an avatar, name, department, and an online/offline indicator (green dot = online/busy, grey = away/offline).
- A mock "Message on Slack" icon button is shown per manager; it only opens a Slack deep link (`slack://user?...`) when the manager is online, and is disabled/greyed out otherwise.
- `data/staff.ts` exposes `getManagersOnDuty()`, selecting staff members with managerial roles (`FLEET_MANAGER`, `OPERATIONS_MANAGER`, `SUPERVISOR`).

## 67.4 White / Light Theme Template

- A second visual template — a white/light theme — is available as a toggle, in addition to the default dark Tokyo Nights theme.
- Implemented via CSS custom properties (RGB triplets) in `app/globals.css` under `:root` (dark, default) and `.theme-light` (light override). Tailwind's color tokens (`bg`, `fg`, `accent`, `status`) reference these variables via `rgb(var(--color-x) / <alpha-value>)` so existing component classes work unchanged in both themes.
- A `ThemeToggle` component (sun/moon icon button) in the top bar toggles the `theme-light` class on `<html>` and persists the choice to `localStorage`.
- A small inline script in `app/layout.tsx` applies the stored theme class before hydration to avoid a flash of the wrong theme.

## 67.5 World Clocks (Top Bar)

- The top bar displays live clocks for three continents: Johannesburg (Africa), London (Europe), and Dubai (Asia), updating roughly every 30 seconds.
- Implemented as a client-only `WorldClocks` component using `Intl.DateTimeFormat` with explicit `timeZone` values, rendered inside `TopBar.tsx`.

# 68. Session 3 Polish & Bug Fix Requests

The following issues were reported after Session 2's animation/navigation work shipped, and have been implemented. Recorded here for context so future changes remain consistent with them.

## 68.1 Card Stack Height + Collapsible Cards

- Card stacks (Active Operations, Truck Activity, Driver Activity, Open Tickets, Activity Timeline) must never grow taller than the visible browser window — each list scrolls internally instead of pushing the whole page down.
- Implemented with a `max-h-[65vh] overflow-y-auto` scroll region per panel (class `card-stack` in `app/globals.css`, see 68.3) rather than relying on ambiguous `flex-1`/`h-full` chains.
- Individual cards (`EventCard`, `TruckCard`, `DriverCard`, `TicketCard`) are now collapsible: they render a compact single-line summary (status + title/registration/name + a chevron) and expand to show full detail (description, location, telemetry, assignment) on click. Cards start collapsed by default so more of the stack is visible at once within the capped height.

## 68.2 Active Operations Header Layout

- The "Active Operations" title previously sat on the same row as the filter tabs (All / Emergencies / Delays / Normal), causing crowding.
- Fixed by stacking the title above the tab row in `EventFeed.tsx` (title on its own line, tabs wrap below it).

## 68.3 Removed Card Glow Effect

- The `shadow-glow-critical` / `shadow-glow-warning` box-shadow glow on critical/warning `EventCard`s has been removed — it did not read well visually. Cards now rely on border/background tint only for severity emphasis.
- A `.card-stack { scrollbar-gutter: stable; }` rule was added to `app/globals.css` and applied to all scrollable card-stack containers, reserving space for the scrollbar so cards don't visibly shift in width when a scrollbar appears/disappears during an update.

## 68.4 Delay Indicator Mismatch

- The "Potential Delays" and "Emergencies" tiles in `OperationsSummary` previously counted WARNING/CRITICAL-severity *events* (including vehicle/driver alerts that never change a truck's status), which frequently disagreed with the number of trucks actually shown as `DELAYED`/`EMERGENCY` in the Fleet list.
- `calculateSummary()` in `simulation/SimulationState.ts` now counts trucks whose `status` is `DELAYED` (Potential Delays) or `EMERGENCY` (Emergencies) directly, so the top indicators always match what's visible in Truck Activity / Fleet view.

## 68.5 Emergencies Float To Top + Reduced Frequency

- `EventFeed.tsx` previously sorted only by recency (`lastUpdated`), so a CRITICAL event could sit below more-recently-touched NORMAL/WARNING events. It now sorts by severity first (CRITICAL, then WARNING, then NORMAL) with recency as the tiebreaker, matching the existing status-priority sort already used by Truck Activity and Driver Activity.
- Emergency events are now rarer: the `EMERGENCY` generation weight in `simulation/EventGenerator.ts` was reduced (redistributed into `NORMAL`), so fewer emergencies are generated overall.

## 68.6 Reduced Simultaneous Updates

- The simulation tick interval (`simulation/SimulationClock.ts`) was increased so ticks happen less often, giving each animation more time to settle before the next change.
- The per-tick chance of generating a brand-new event (`SimulationEngine.tick()`) was reduced.
- `progressExistingEvents()` and `progressTickets()` in `simulation/EventProcessor.ts` now stop after the first mutation per tick instead of looping through every event/ticket and potentially resolving/escalating several at once — this keeps each tick's visible change count small and readable instead of several cards animating simultaneously.

# 69. Session 4 Fixes & Driver Location Map

## 69.1 Hydration Mismatch Fix

- A React hydration warning was occurring because the no-flash theme script in `app/layout.tsx` adds a `theme-light` class to `<html>` before React hydrates, which the server-rendered markup does not have.
- Fixed by adding `suppressHydrationWarning` to the `<html>` element — this is an intentional, expected pre-hydration DOM mutation, not a real mismatch.

## 69.2 Content Shift During Card Animations

- Card stacks were shifting in width whenever a card animated in, reordered, or was removed.
- Root causes fixed: (1) `framer-motion`'s `layout` prop (full size+position tweening) was replaced with `layout="position"` on all animated cards (Event, Truck, Driver, Ticket, Timeline) so cards no longer apply a scale-correction transform when siblings resize. (2) The outer page (`html`) and the dashboard's scrollable `<main>` region (`components/dashboard/DashboardApp.tsx`) did not reserve space for their scrollbars, so the whole layout narrowed/widened as the page's scrollbar appeared and disappeared on every tick — fixed with `scrollbar-gutter: stable` on both.
- Cards briefly rendering outside their own card-stack box during reflow was caused by `AnimatePresence mode="popLayout"` positioning the reflowing/exiting card as `position: absolute` relative to the nearest positioned ancestor; none of the card-stack containers had `position: relative`, so a card could pop out relative to a distant ancestor. Fixed by adding `relative` to each card-stack scroll container.

## 69.3 Driver Location Map (Mockup)

- Added a schematic (non-GPS, mockup) network map showing each on-duty driver's current location and delivery destination, visible in the **Drivers** sidebar view above the driver list.
- `types/logistics.ts` `Location` now carries schematic `x`/`y` percentage coordinates (0–100 / 0–60) used purely for this mock map layout; `data/locations.ts` assigns coordinates to all 16 known locations and exposes `getLocationCoords(name)`.
- `domain/TruckDriver.ts` now tracks a `destination` field alongside `currentLocation`. `startRoute(destination)` sets it when a driver departs; `arrive(location)`/`completeDelivery(nextDestination)` (reworked in 69.5) keep it accurate as the simulation runs. `simulation/EventProcessor.ts` supplies these values from `DEPARTURE`/`ARRIVAL`/`DELIVERY` events.
- **Tied into the delay system**: each driver's route line and current-location marker on the map are colour-coded by their live status — blue for on route, amber for delayed, red (pulsing) for emergency, muted/dashed for idle/off-duty — using the same status source as the Truck/Driver Activity cards and the `OperationsSummary` delay/emergency tiles, so the map always agrees with the rest of the dashboard.
- The `DELAY` event handler in `EventProcessor.ts` now also marks the linked driver `DELAYED` (previously only the truck was marked), and resolving a `WARNING` event now resets the driver back to `ON_ROUTE` as well (previously only the truck was reset) — keeping driver status consistent with truck status for the map and for Driver Activity.
- Clicking a marker on the map selects that driver and shows a small detail strip (name, truck registration, current → destination, status badge) below the map. New component: `components/dashboard/DriverMap.tsx`.

## 69.4 Driver Routes Redesigned As A Stop List

- The schematic SVG map with drawn lines across a canvas didn't read as realistic, so `components/dashboard/DriverMap.tsx` was redesigned around the same underlying data (coordinates are no longer rendered — `x`/`y` remain in the data model but are unused by this component).
- New layout: a scrollable driver list on the left (sorted emergency → delayed → on route → idle, click to select) and a route detail panel on the right showing the selected driver's stops as a vertical two-step list — **Current location** and **Next stop** — each labelled with its location type (Depot, Distribution Centre, Customer Site, etc.) from `data/locations.ts`, connected by a coloured line/dot matching the driver's live status tone (info/warning/critical/muted), with a pulsing marker for delayed/emergency drivers.
- The first driver in the sorted list is auto-selected by default so the route panel is never empty.

## 69.5 Truck/Driver Status & Location Fully Synchronized

- **Root cause 1 (initial data)**: `data/trucks.ts` and `data/drivers.ts` previously picked each linked truck's and driver's `status` and `location` from two independent random pools, so a truck could start `ON_ROUTE` while its driver started `OFF_DUTY`, immediately making the "Trucks on route" summary tile disagree with the Driver Routes list. Fixed: `createDrivers(trucks)` now takes the generated trucks and derives each linked driver's `currentLocation` directly from their truck's `location`, and their `status` from a `truckToDriverStatus` map (`ON_ROUTE`/`LOADING`/`UNLOADING`/`DELAYED`/`EMERGENCY` mirror 1:1; a truck sitting `AVAILABLE` maps to a resting/off-duty driver).
- **Root cause 2 (ongoing simulation)**: the delivery lifecycle only had two phases (`DEPARTURE`, `DELIVERY`) but three truck states (`LOADING`, `ON_ROUTE`, `UNLOADING`), so an arriving truck moved to `UNLOADING` while `EventProcessor.ts` simultaneously forced its driver straight back to `ON_ROUTE` with a brand-new destination — a permanent mismatch every time a delivery event fired.
  - Fixed by giving the lifecycle a proper 3-phase loop shared by truck and driver: `LOADING` → (`DEPARTURE` event) → `ON_ROUTE` → (`ARRIVAL` event) → `UNLOADING` → (`DELIVERY` event) → back to `LOADING`. `simulation/scenarios/deliveryScenario.ts` now emits `DEPARTURE` while `LOADING`, `ARRIVAL` while `ON_ROUTE` (previously unused by the generator despite already existing as an `EventType`), and `DELIVERY` while `UNLOADING`.
  - Added `domain/TruckDriver.ts#arrive(location)` so the driver moves to `UNLOADING` at the same location as the truck (`Truck#arrive`); `completeDelivery(nextDestination)` was simplified to move the driver back to `LOADING` (matching `Truck#startLoading()`) and assign the next destination, instead of incorrectly jumping to `ON_ROUTE`.
  - Arrival locations are now taken from the driver's own `destination` field (where they were actually headed) instead of a fresh random location, so a truck/driver always "arrive" where they said they were going.
- Net effect: at every point in the simulation, a truck's status/location and its linked driver's status/location are derived from the same transition and can no longer drift apart, so summary counts (e.g. trucks on route) always match the Driver Routes view.

## 69.6 "Potential Delays" Undercounting Fix

- The "Potential Delays" tile could show 1 even when 2+ trucks were actually `DELAYED`. Root cause: `progressExistingEvents()` in `simulation/EventProcessor.ts` resolved *any* unresolved `WARNING`-severity event (rolling a 15% chance per event per tick) and, whenever it did, reset that event's linked truck/driver back to `ON_ROUTE` if they happened to currently be `DELAYED` — but `VEHICLE_ALERT` and `DRIVER_ALERT` events also use `WARNING` severity and are unrelated to the delay. So resolving an unrelated vehicle/driver alert for a truck that was separately delayed by a real `DELAY` event would silently clear its `DELAYED` status, while the actual `DELAY` event stayed open. The more simultaneous delays/alerts existed, the more often this fired, pulling the visible count back down toward 1.

## 69.7 "Potential Delays" Showing 0 While "Delays" Tab Had Entries

- After 69.6, the tile could still read `0` while the "Delays" tab in Active Operations showed entries. Root cause: `EventFeed.tsx`'s "Delays" tab filtered purely by `event.severity === "WARNING"`, but `VEHICLE_ALERT` and `DRIVER_ALERT` events (e.g. "Tyre pressure warning", "Fuel level below threshold") also use `WARNING` severity despite never touching a truck's `DELAYED` status. These non-delay warnings were filling the "Delays" tab while the `potentialDelays` tile (which only counts trucks whose `status === "DELAYED"`) correctly showed 0, since no truck was actually delayed.
- Fixed by special-casing the `filterEvents()` logic in `EventFeed.tsx`: when the active tab is `"WARNING"` ("Delays"), it now filters by `event.type === "DELAY"` specifically instead of by severity, so only genuine delay events appear there and the tab always agrees with the summary tile. The "All", "Emergencies", and "Normal" tabs are unaffected.
- Fixed by only resetting truck/driver status back to `ON_ROUTE` when the event actually being resolved is `event.type === "DELAY"` — resolving a vehicle/driver alert no longer touches delay status. Each delay now only clears when its own `DELAY` event resolves, so the "Potential Delays" tile accurately reflects however many trucks are truly `DELAYED` at once.
